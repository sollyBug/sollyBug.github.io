### 📝 2. User Stories and Tasks

#### 2.1 Overview

User stories describe what a user needs from an application and why that functionality is important. They are usually written from the user's perspective, using a format such as: > As a user, I want something to happen, so that I can achieve a particular goal.

During my internship, most of the work I've received has been in the form of development tickets. These tickets normally describe a bug or improvement that needs to be investigated. Although they aren't always written as traditional user stories, they still describe functionality that affects the people using the application.

I've used two examples from my internship to demonstrate how these tickets can be understood as user stories and broken down into smaller development tasks.

#### 2.2 User Story 1 - Duplicate Tax Assignments

**User Story**

> As an administrator importing products, I want each tax to be assigned only once, so that importing repeated tax names does not create duplicate assignments.

**Background**

I was working on an issue where customers could end up with duplicate tax assignments when importing data from a spreadsheet. The problem occurred when the same tax was listed more than once. I reproduced the issue in the web console and also used my local database to check the resulting records.

After investigating the problem, I implemented a correction and tested whether the duplicate assignments were still being created. While working on this, I discovered that the product importer had a similar problem. This became another development ticket that needed to be investigated separately.

**Acceptance Criteria**

- Repeated tax names should only result in one assignment for each unique tax.
- Different taxes should still be assigned correctly.
- Importing records without duplicate taxes should continue working as expected.
- The correction should not affect unrelated import functionality.

**Tasks Involved**

| Task | What I Did |
|---|---|
| 1. Investigate | Reviewed the ticket and reproduced the issue. |
| 2. Verify | Checked the duplicate assignments in the application and database. |
| 3. Debug | Investigated how tax values were processed during imports. |
| 4. Implement | Worked on preventing repeated tax assignments. |
| 5. Test | Checked that duplicate values no longer produced repeated assignments and that normal cases still worked. |
| 6. Review | Prepared the changes for the normal review process. |

The customer-import issue was corrected, and I worked on the similar product-import problem afterward.

#### 2.3 User Story 2 - Creating a Blank Order

**User Story**

> As a user creating a new blank order, I want the previous order's information to be cleared correctly, so that I can start a new order without unintended information being carried over.

**Background**

Another issue I worked on involved creating blank orders. The application wasn't always clearing the previous order's information correctly. What made this issue interesting was that the behaviour changed depending on whether the previous order contained items. When the cart was empty, information from the previous order could remain when creating a new blank order. I investigated the state-handling logic and worked on correcting the behaviour while keeping the expected customer-selection functionality. I also added a Playwright test for the scenario.

**Acceptance Criteria**

- A new blank order should start with an empty cart.
- Previous order details that should not be retained must be cleared.
- Customer selection must behave correctly based on the active customer mode.
- The issue should be covered by an automated regression test.

**Tasks Involved**

| Task | What I Did |
|---|---|
| 1. Reproduce | Tested the behaviour when creating blank orders under different conditions. |
| 2. Compare | Checked the difference between orders with items and orders with an empty cart. |
| 3. Investigate | Looked into how document and customer information was being cleared. |
| 4. Fix | Updated the relevant state-handling behaviour. |
| 5. Test | Verified the corrected functionality and added Playwright coverage. |

### 🔄 4. Sprint Backlog

#### 4.1 Overview

A Sprint Backlog is used in Scrum to keep track of work selected for a particular sprint. It helps developers understand what they're working towards and what needs to be completed during that period.

At Onsight, I've gained experience working on tickets that move through development, testing, code review and integration. I've also contributed work across two code release cycles. Although a code release isn't necessarily the same as a Scrum sprint, these experiences have helped me understand how development work is planned and prepared for delivery. More recently, our team started introducing a four-day development cycle.

#### 4.2 How My Development Work Progresses

When I start a ticket, I first need to understand the reported issue. From there, I investigate the code, implement a solution and test the result. Once I'm satisfied that the change works, I submit it for review. The review process may identify something that needs to be adjusted, which means the task isn't always finished immediately after the first implementation. I've learned to think about the full process rather than only the time spent coding. The table below shows how I understand the main stages of my development work.

| Activity | What Needs to Happen |
|---|---|
| Investigation | Understand and reproduce the reported issue. |
| Development | Implement the required changes. |
| Testing | Check that the correction works as expected. |
| Pull Request | Submit the changes for review. |
| Code Review | Respond to feedback and make adjustments if required. |
| Integration | Confirm that the changes have been merged. |
| Release | Confirm whether the changes have been included in a release. |

This is a breakdown of my development workflow rather than an official Scrum sprint backlog.

#### 4.3 My Experience with Code Releases

So far, I've been involved in development work associated with two code releases. During these release cycles, I worked on assigned tickets, tested my changes and submitted pull requests for review. The experience helped me understand that completing a fix on my local machine doesn't mean the work is automatically ready for the application. There are still review and integration steps that need to happen. I also became more familiar with using Git and pull requests to manage changes.
