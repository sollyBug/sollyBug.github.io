CONTEXT / MY EXPERIENCE

Learning Agile through real software delivery

During my Work Integrated Learning placement, I contribute to maintaining and improving a web application as part of the Web Console team. My work has included frontend bug fixes in the Quasar/Vue interface, regression testing with Playwright, investigations into application behaviour and, more recently, backend changes.

The team uses Jira to coordinate work, daily stand-ups with the wider development teams, code review, and testing before releases. Work is ticket-driven rather than arranged into formal Scrum sprints. This portfolio connects those experiences to Agile concepts while making clear which artefacts are workplace evidence and which are my own academic reflections.

PERSONAL REFLECTION / 10 MARKS

Turning routine practices into working agreements

At university, I learned Agile through structured roles and documents. During WIL, I have experienced a more practical, ticket-driven approach. The team does not need a formal charter for me to observe values such as communication, accountability and code quality in its daily work.

Writing my own proposed charter helped me make those expectations more deliberate. For example, I now see that a ticket is not complete just because I have written a fix: it needs testing, review and clear communication about its status. I also understand the importance of speaking up about blockers during stand-ups rather than leaving others to assume work is progressing.

Going forward, I want to organise my tasks more consistently and prepare clearer summaries before requesting a review. This charter is a way of holding myself accountable, not a replacement for Onsight's procedures.

User Stories & Tasks

Examples of converting real bug reports into testable development tasks.

The examples below are student-written user-story interpretations of tasks I worked on; they are not presented as verbatim Jira stories. They illustrate how I understand requirements from the end user's perspective.

BACKEND · DATA QUALITY

Prevent duplicate customer tax assignments

User story: As a user importing customer records, I want repeated tax names in an import to create only one assignment so that customer tax information remains accurate.

Tasks: Reproduce the issue · identify where duplicates are created · change the assignment logic · verify database results · submit the change for review.

Acceptance check: Repeating a tax in one imported row does not create repeated tax assignments.

BACKEND · DATA QUALITY

Prevent duplicate product tax assignments

User story: As a user importing products, I want repeated applicable tax names to be treated as one selection so that a product does not receive duplicate tax associations.

Tasks: Confirm the similar failure · apply deduplication after matching tax types · test repeated values · prepare and submit the fix.

Acceptance check: Duplicate tax names in an imported row result in a single applicable tax association per tax.

FRONTEND · USER EXPERIENCE

Improve mobile document readability

User story: As a mobile user, I want document information to remain readable on a small screen so that I can review it without losing important details.

Tasks: Inspect the existing layout · explore mobile presentation options · preserve desktop behaviour · test smaller screen widths · document the alternatives.

Acceptance check: Mobile document information is readable and key fields remain accessible without breaking desktop presentation.

PERSONAL REFLECTION / 10 MARKS

From a ticket description to a verified fix

One of the biggest lessons from working on real tickets has been learning not to rush straight into coding. I first need to reproduce the problem and understand the expected behaviour. On import-related issues, that also meant checking how the application stored its data, rather than relying only on what appeared in the interface.

Reviewing similar customer and product import problems helped me recognise recurring patterns and reuse an appropriate problem-solving approach without assuming that every part of the system behaves identically.

I have also learned that a good task includes evidence of the fix: clear testing steps, a meaningful pull request and a willingness to respond to review comments. In future, I want to document my acceptance checks before implementation so that testing is more focused.

PERSONAL REFLECTION / 10 MARKS

Understanding priorities and the bigger picture

Before my WIL placement, I mainly thought of backlogs as lists created during project planning. Using Jira has shown me that the backlog and board are active coordination tools. I can move between the team's wider view and my own assigned work, which helps me understand where my tasks fit into ongoing maintenance and releases.

When a release is approaching, testing and review readiness become as important as starting additional work. At other times I can take the next available ticket, investigate it and communicate my progress during the daily stand-up. I have learned not to confuse being busy with delivering useful, verifiable changes.

My next improvement is to record dependencies and blockers earlier so that teammates have a clearer view of the work I can realistically finish.

PERSONAL REFLECTION / 10 MARKS

Thinking beyond “code complete”

Participating in two code releases helped me understand that delivering a change involves more than implementing the solution. A ticket needs to be reviewed, merged and tested at the appropriate stage before it can be considered ready. This has encouraged me to think about the full delivery process instead of focusing only on the part I am coding.

Our work is release-driven rather than organised into formal Scrum sprints. That has challenged me to manage my own workload carefully and to be realistic about what I can complete before reviews and testing take place. It has also made communicating unfinished work important, because outstanding items affect planning for everyone.

A new four-day development, team-review, and merge-and-test cycle has recently been introduced. I have not yet completed a cycle, so I see it as a future opportunity to make my progress and review preparation more consistent, not as past evidence.

PERSONAL REFLECTION / 10 MARKS

Using reflection to notice progress

Daily stand-ups encourage me to explain what I worked on previously, what I intend to do next and where I need help. Over time, that routine has improved how I summarise technical problems and communicate with developers from different teams.

Looking back at my work also makes my growth more visible. I started by becoming familiar with the application and frontend testing. Later, I became more confident investigating complex behaviour and recently began working on backend problems involving imported data. Code review remains an important learning opportunity because it exposes me to other developers' ways of thinking.

I want to keep a more consistent personal log of decisions, test results and feedback. This should make my stand-up updates clearer and help me carry lessons into future tickets.

OVERALL REFLECTION

What has changed since my first-semester portfolio?

My earlier academic work focused mainly on demonstrating technical knowledge through university projects. During WIL, I have begun to understand what it takes to contribute to a system that is already being used: tracing existing behaviour, considering regression risks, collaborating through pull requests and following work through review and testing.

The transition from frontend tasks into backend bug fixes has been particularly valuable. It has shown me that solving a visible problem may require understanding data flow, business rules and the behaviour of several parts of an application. My next goals are to improve the clarity of my technical communication, strengthen my testing habits and contribute with increasing independence while continuing to learn from code review.
